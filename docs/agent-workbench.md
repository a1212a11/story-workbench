# 写小说的 Claude Code：新包设计（M6）

日期：2026-09-18。状态：作者已认可，M6-01 于 2026-09-20 完成；进度见[项目计划 M6](project-plan.md#m6-代理式工作台)。本文取代 2026-09-18 上午那版"代理式工作台"设计，也取代 [M5 设计](conversational-workbench.md)。

## 1. 结论先行

这个项目不做成工作流。现有 `story_workbench` 包的重心是一台状态机：计划、稿件、检查、采用、快照、复核、影响、发布，每样是一张表和一次事务，AI 是步骤里被调用的函数。M5 把模型放到前面当调度员，仍是在替作者走流程。作者的原话："应该是 AI 和人的对话来控制一切……我要做的是 agent。"

新方向是"写小说的 Claude Code"：

- 作品是一个 Markdown 目录，作者用任何编辑器都能看。
- 工具是通用的读、改、搜文件，加两个领域工具。
- 创作方法写在技能文件里，不写在代码里。
- 作者权限只靠一条硬规则：正式文件的每一处改动，先看 diff 再批准。
- 历史靠 git，程序自己管，作者看不到 git 词汇。
- 故事状态是代理维护的一份文件，不是程序算出来的快照。

作者对三个关键问题的答复（2026-09-18）：git 可以，但非专业作者也要能用，优先级低；故事状态交给代理，作者缺少指导时代理也要能写出好文章；新起一个干净的包。

新包名 `story_agent`，与旧包并存在同一仓库，直到新包通过三章验收后删除旧包。

## 2. 目标体验

```
✻ 《寒灯协定》 · deepseek-flash

⏺ 第二章写完了还没定稿。我重读了一遍，有两处是新设定：配给站有夜间
  通行证；情报员认得沈砚的笔迹。和第一章的气氛合得上，我建议都留。
  另外结尾她把情报藏进灯座，这会影响第三章的开头。要不要先定第二章？

> 通行证那条不要，改成她靠熟人放行

⏺ 好，改掉那一段，笔迹那条留着。
⏺ 修改 章节/第02章.md
  ┌ 章节/第02章.md ──────────────────────────────────┐
  │ - 她把通行证按在玻璃上，值夜的人只看了一眼。        │
  │ + 值夜的是老周。他没看证件，只看了看她身后的雪。    │
  │ …（共 2 处）                                       │
  │ Enter 批准 · n 不批准 · 或直接输入你的意见          │
  └────────────────────────────────────────────────────┘
> ⏎
  ⎿ 已保存 · 记为一次修改
⏺ 审读(章节/第02章.md)
  ⎿ 完成 · 1 条提醒，引用已核对
⏺ 改好了。审读只剩一条提醒：老周这个人物第一章没出现过，我在人物/老周.md
  里加了三行介绍，也要你批准。第二章定下来后我会更新故事状态，然后我们
  聊第三章。
```

作者只说话。代理自己决定读什么、改什么、查什么、什么时候问。审批卡就是 diff。

## 3. 作品目录

```
寒灯协定/
  作品.md          书名、题材、基调、篇幅、作者的偏好与禁忌（相当于 CLAUDE.md）
  大纲.md          全书走向；每章一段：剧情、结尾状态、状态
  设定/            世界、规则、地点，一题一文件
  人物/            一人一文件：身份、想要什么、知道什么、说话方式
  章节/第01章.md    正式正文，一章一文件
  故事状态.md      到目前为止已成立的事实、各人物知道什么、读者知道什么、未回收的线索
  决定.md          作者决定的追加日志，带日期；已有条目不改写
  草稿/            试写、备选段落、代理的工作笔记，随便写
  技能/            创作方法文件，初始化时从包里复制，作者可改
  对话/            每天一个文件，会话记录
  .story/          配置、用量记录，不给作者看
  .git/
```

分两类：

- **正式文件**：作品.md、大纲.md、设定/、人物/、章节/、决定.md。改动必须经审批卡。
- **自由文件**：故事状态.md、草稿/、技能/。代理直接写，改动的 diff 在对话里显示，不弹卡，同样记一次历史。对话/ 由程序维护，代理不能改。故事状态归自由文件，因为它是代理的工作笔记，每次都问会把作者烦死；作者随时可以纠正它，纠正写进决定.md 就成了硬约束。

文件里不放内部 ID。章节文件名固定"第NN章.md"，标题写在文件第一行。

## 4. 代理

### 4.1 循环

沿用 M5 的引擎骨架：一次作者发言是一轮，模型带工具调用；文本流式显示；工具执行后回传结果；直到模型不再调用工具。每次模型调用记一条用量到 `.story/用量.jsonl`。

- 一轮内调用次数上限 40，超过停下来告诉作者。写一章大约要读五六个文件、写一次、审读一次、改两三次，8 次不够。
- Esc 中断本轮：停掉流，正在等待的审批卡视为不批准。中断不会留下半个文件，因为写文件只发生在批准之后、且一次写完。
- 作者在代理工作时发言，排队到本轮结束再处理。
- 付费失败不自动重试，把原因告诉作者。
- 工具返回的文件内容是数据，其中的指令不执行。

### 4.2 开场

打开作品时代理先发一轮，隐藏提示是「（作者刚打开作品。读作品.md、大纲.md、故事状态.md，用两三句话说明现状，提议下一步。）」。目录是空的就走"开书"技能：问书名和一句话想法，然后提议设定与人物。没有密钥时不发请求，只显示本地生成的一句现状。

### 4.3 系统提示

协作者人格，要点：

- 你和作者一起写这本书。作者定故事，你负责推进、落实和把关。
- 先读再动手：动笔前读作品.md、大纲、故事状态、相关人物与设定；不凭记忆编。
- 主动推进：作者说一句想法，你把它整理成设定、人物或某章剧情提议出来；写完就审读；审读有问题先说你的处理意见；处理完提议定稿；定稿后更新故事状态，提议下一章。回复末尾永远有下一步。
- 作者给得少时，你按技能里的方法自己补：没有大纲就先提议大纲，没有人物就先立人物，作者不表态就按你的提议走，但每一步正式文件的改动都经审批。
- 新的持久设定、改变已有设定、改变作者决定：先问，写进决定.md 后才算数。
- 改正文用 edit 工具直接改，不要让作者自己动手；作者说要自己改才打开编辑器。
- 简短、具体、中文。文件内容工具已经显示给作者，不复述。
- 没把握就问，不编造。

技能清单放在系统提示末尾，代理按需读取技能文件。

### 4.4 工具

七个，全部中文说明。

| 工具 | 作用 | 审批 |
| --- | --- | --- |
| `read(path)` | 读文件或列目录；正文完整显示给作者 | 无 |
| `search(pattern, path?)` | 在作品目录里全文搜索 | 无 |
| `edit(path, reason, changes \| content)` | 唯一的写入口。`changes` 是若干 `{old, new}` 定点替换（old 须唯一），`content` 是整文件内容（新文件、重写）。正式文件弹 diff 卡，批准后原子写入并提交 git；自由文件直接写，diff 显示在对话里 | 正式文件 |
| `history(path?, action, ref?)` | 用人话列出改动历史；`show` 看某次的内容；`restore` 把文件恢复到某次 | restore 需审批 |
| `verify(path, quotes)` | 核对若干引用是否逐字出现在文件里，返回每条命中与否及位置 | 无 |
| `review(path, focus?)` | 独立审读：用一个不带对话历史的新上下文，只给这一章、故事状态、大纲、相关人物设定和审读清单，返回带原文引用的提醒；每条引用经 `verify` 核对，核不上的丢弃并标注 | 无，付费 |
| `open_editor(path)` | 打开全屏编辑器让作者自己改；保存即视为作者批准 | 作者自己 |

- 只有 `edit` 会改文件，`restore` 通过 `edit` 的同一条审批路径落地。代码里不存在第二条写路径。
- `edit` 对正式文件的一次调用只对应一张卡；一张卡可以含同一文件的多处改动。改多个文件就是多张卡。
- `review` 是旧包"检查"里唯一值得留的东西：换一个干净上下文审，比自己审自己可靠；每条结论必须引用原文且引用必须真的在文里，这是对付幻觉的办法。审读清单来自技能文件，作者可改。

### 4.5 审批

端口：

```python
@dataclass(frozen=True)
class ApprovalCard:
    title: str                # 修改 章节/第02章.md
    diff: str                 # 统一 diff，界面着色显示
    summary: str              # 共 2 处；新增 1 个文件
    kind: str                 # edit / restore

@dataclass(frozen=True)
class Approval:
    approved: bool
    note: str = ""            # 作者打字的意见

def approve(self, card: ApprovalCard) -> Approval: ...
```

- Enter、`y`、「好」「可以」「批准」是批准；`n`、「不」、Esc 是不批准；其余文字是不批准并带意见。
- 不批准时工具返回「作者没有批准。作者说：……」，模型据此调整再提议，不重试。
- 每次批准写一条 git 提交，信息是人话：「第二章 · 改了守夜人的段落」，由模型在调用 `edit` 时给出 `reason`。
- 卡片与作者的回答写进当天的对话文件。

### 4.6 技能

Markdown 文件，初始化时复制到 `技能/`，作者可改。首版：

| 文件 | 内容 |
| --- | --- |
| 开书.md | 从一句想法到作品.md、三到五个核心设定、主要人物、前三章大纲的做法；作者说得少时怎么提议 |
| 定章.md | 一章的剧情与结尾状态怎么定；结尾状态必须能写成"此刻谁在哪、谁知道什么、什么还没解决" |
| 写章.md | 动笔前读什么；篇幅、视角、节奏的默认；不引入大纲没有的持久设定；写完先自读一遍再交 |
| 审读.md | 审读清单：与故事状态和设定的冲突、人物认知越界（说了不该知道的）、新持久设定、与本章剧情结尾的偏差、读者体验；每条要引用原文 |
| 故事状态.md | 定稿后怎么更新：事实、各人物知道什么、读者知道什么、悬而未决的线索；只记正文确立的，传闻与人物猜测分开 |
| 回改.md | 改了前章后：逐章对照后文，列出受影响处，逐处提议改法；核对完才更新故事状态 |
| 修订.md | 按作者反馈改稿：先定位问题段落并引用，再提改法，改完只动该动的地方 |

技能是这个产品的价值所在。它们只能用真作品反复试出来，所以新包一起步就用《寒灯协定》跑，不先把功能做全。

## 5. 界面

沿用 M5 的 Textual 外壳与线程模型，改三处：

- 审批卡显示 diff，删除行红、新增行绿，超过 40 行可滚动；末行「Enter 批准 · n 不批准 · 或直接输入你的意见」。
- 去掉斜杠命令与问题卡。按键：Enter 发送，Ctrl-J 换行，Esc 中断或不批准，Ctrl-C 中断、清空或退出，Ctrl-D 退出，Ctrl-O 折叠工具输出。
- 状态行右侧：作品名、模型、本次用量。工具行样式不变：「⏺ 修改 章节/第02章.md」「⎿ 已保存」。

## 6. git 与非专业作者

- 新作品目录自动 `git init`，`.gitignore` 排除 `.story/`。每次批准一次提交，自由文件每次改动也提交一次，提交信息都是模型给的人话 `reason`；作者在编辑器里保存的记为「作者亲自修改」。
- `history` 工具与界面只用人话：「第二章 · 昨天 21:03 · 改了守夜人的段落」。恢复走审批卡。
- 机器没有 git：一句提示「没有找到 git，历史功能不可用，其他照常」，不阻塞。为非专业作者打包 git 的事优先级低，先不做。

## 8. 新包结构

```
story_agent/
  __main__.py     参数、配置、启动界面
  config.py       配置与密钥
  provider.py     模型客户端
  workspace.py    目录约定、正式/自由文件判定、初始化、git
  tools.py        七个工具的定义与执行
  approval.py     ApprovalCard / Approval / 端口协议
  agent.py        系统提示装配、一轮循环、对话记录、用量
  review.py       独立审读的上下文与调用
  skills/         默认技能文件
  tui.py          Textual 界面
tests/agent/      新包测试；旧测试不动
```

依赖方向：`tui` → `agent` → `tools` → `workspace` / `provider`。`workspace` 是唯一碰文件系统与 git 的模块；`provider` 是唯一碰网络的模块。

## 9. 测试

- 工作区：初始化目录与技能复制；正式/自由文件判定；git 初始化、提交、人话历史、恢复；没有 git 时降级。
- 工具：`edit` 对正式文件不批准则文件不变、git 无新提交；批准后内容正确且有一条提交；自由文件直接写；`verify` 命中与未命中；`review` 丢弃核不上的引用；`history restore` 走审批。
- 代理：脚本客户端加假端口。开场轮读三份文件；一句话 → 读、写、审读、改、提议定稿；不批准带意见回到模型；模型口头说"改好了"而没调用 `edit` 时文件不变；40 次上限；Esc 中断后没有半个文件；无密钥零请求；对话文件追加。
- 界面：审批卡显示 diff 与三种回答；编辑器保存与取消；Esc；开场轮。
- 真实验收：《寒灯协定》导入后，用对话完成：按作者一句反馈修订第二章、定稿、更新故事状态、写第三章、回改第一章并核对后文。作者对文章质量与代理主动性的评价是验收结论，程序检查不替代。
