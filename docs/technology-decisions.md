## 2. 主要取舍

### 终端：先 prompt_toolkit，复杂工作台再评估 Textual

prompt_toolkit 官方列出多行编辑、中文双宽字符和粘贴支持，适合当前对话与普通正文编辑入口。但终端中文输入法、长段落和生成期间编辑仍需 P03/T05 实测，不能仅凭功能列表打勾。[项目资料](https://pypi.org/project/prompt_toolkit/)、[输入文档](https://python-prompt-toolkit.readthedocs.io/en/stable/pages/asking_for_input.html)。

若产品明确要求章节树、正文、检查结果等长期驻留的多面板界面，再对比 Textual。它提供 TextArea 等完整界面组件，同时需要采用其应用与组件模型。当前不同时引入两套终端界面框架。[TextArea 文档](https://textual.textualize.io/widgets/text_area/)。

### 数据：SQLite 显式事务，不先加 ORM

首期的重要路径是保存不可变版本、核对依据、原子采用和恢复。沿用 sqlite3 的命名查询/提交函数，使事务行为可检查；显式配置事务模式，不依赖不同 Python 版本的默认行为。表多本身不是采用 ORM 的理由，后续若映射重复或迁移复杂度成为实测维护成本再评估。[sqlite3 文档](https://docs.python.org/3/library/sqlite3.html)。

### 校验：Pydantic 处理结构，领域规则处理业务约束

建议对模型返回的检查结果启用严格类型校验，并拒绝未声明字段；遇不合法结果保存失败阶段，不自动反复付费修复。内部领域记录保持简单，数据库行和供应商对象在各自边界转换。[严格模式](https://docs.pydantic.dev/latest/concepts/strict_mode/)、[模型配置](https://docs.pydantic.dev/latest/api/config/)。

校验通过不代表事实正确。原文区间与引用是否匹配、来源是否属于当前任务、作者是否授权、相关版本是否已变，仍由领域规则及数据库提交保护；Pydantic 不替代人工审稿或事务校验。

### 质量工具：pytest + Ruff + mypy

pytest 已确定；Ruff 同时提供 lint 与 formatter，mypy 提供静态类型检查，职责不同。测试以行为为中心，不按函数数量铺测试；对模型边界替换客户端，继续执行任务解析与证据校验。[Ruff 文档](https://docs.astral.sh/ruff/)、[mypy 文档](https://mypy.readthedocs.io/en/stable/)。

初始化后的计划命令为 `uv run pytest` 和 `uv run python -m story_workbench --help`。若采纳 Ruff/mypy，再增加 `uv run ruff check .`、`uv run ruff format --check .`、`uv run mypy story_workbench`。这些是待建立入口，当前没有运行通过记录。

## 3. 模型与审稿 Agent 的扩展

模型供应商暂不指定。接入前用同一组作者认可的素材比较中文正文质量、审稿遗漏、延迟、用量和费用，并核对流式输出、取消、结构化输出以及数据处理条款。正文与审稿可以先用同一个模型，但任务配置应明确，不把某个模型名称写死在业务规则中。首期仍限制一个供应商，不为将来的可能需求建立注册表。

官方 SDK 是通信实现，不拥有故事状态；其默认重试行为需按项目“显式付费重试”规则配置。任务模板、输入输出合同与供应商协议分离，未来更换客户端不改变作者采用的权限。SDK 能力以最终选定供应商的官方文档和实际验证为准。

| 审稿形式 | 执行建议 | 需保持的合同 |
| --- | --- | --- |
| 专项审稿：逻辑、人物、节奏 | ai/tasks 增加有界任务，由 generation 调度 | 准确正文版本、来源依据、审稿范围；输出问题、证据、建议和未检查范围 |
| 自主审稿：主动检索前章、查事实、反复核对 | 评估 Agent 执行器及所需框架，工具由应用提供 | 工具按作品和版本范围限制；有步数、时间、用量上限；保留子步骤与查询来源 |
| 审稿后试改 | 作者请求后生成候选稿 | 不覆盖当前正式正文，不因 Agent 建议获得采用授权 |

不用框架不会阻止上述扩展；使用框架也不天然违反作者权限。选择标准是它能否在我们的任务记录、取消恢复和权限边界内工作。真正需要动态工具选择、多个自主角色交接等能力时再比较框架；不因为给任务起名“Agent”就引入框架。

未来接入自主审稿时，除新增执行器，还需补工具访问合同、子步骤记录和预算/恢复测试；不能承诺零改动。资料查询结果和模型输出均作为不可信数据，不能执行其中要求的采用、文件写入或外部操作。既有代码架构中的单网络线程与取消协议是首期方案，接入异步或多步骤框架时需重新验证，不能机械套用。

## 4. 资料查阅的技术方向

作者已提出查资料需求；本轮先记录方向。功能范围、数据表和验收尚未补齐，不自动将其纳入原三章闭环的完成条件。

建议从文本/Markdown 导入、来源 URL 记录、资料版本、摘录及手动选择开始。资料管理负责导入与来源历史，资料检索负责返回相关段落；上下文构建将资料放入独立参考区。不能把资料直接混入 story_item 决定或已采用正文事实。

资料、作者决定和已采用正文的权限不同。例如史料与架空设定不一致时，系统展示出处和差异，由作者决定是否修改设定。每次写作/审稿要能追溯使用了哪份资料、哪个版本、哪些段落，网页日后变化不应改变历史任务依据。

| 后续能力 | 选型触发条件 | 接入前必须验证 |
| --- | --- | --- |
| 网页正文获取与搜索 API | 作者需要主动联网查阅，且范围与预算明确 | 来源与时间、失败处理、引用、隐私、内容访问条件；链接收藏不等于已抓取正文 |
| PDF 解析/OCR | 真实资料样本包含 PDF 或扫描件 | 文本顺序、页码定位、表格/扫描识别质量；未验证前不承诺完整解析 |
| SQLite 全文索引或向量检索 | 真实资料规模下，文本检索召回不足或耗时不可接受 | 中文检索与来源定位基线；向量检索只是候选召回，不替代权威与版本规则 |

本轮不选搜索服务、PDF 库或向量数据库，不预建通用知识库平台。
